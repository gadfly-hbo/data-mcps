# Red-Team 报告：data-mcps 首期开发 Proposal

**评审对象**：`.flow/proposal.md`（dev-flow 根 spec）——用一个 60 轮 / 12 小时的 auto flow，交付 local-first 外部数据集市与采集工作台的独立天气闭环（全合成数据边界 + 真实适配器接缝 + MCP 接缝 + 四分权限 + 不可变快照 + 10 条失败路径，A16 真实对照留「未执行」）。

**方法**：按 strategy-red-team 执行——先提取全部承重断言，逐条钢人化再攻击，失败模式按（错误影响 × 错误概率 × 测试便宜度）排序，每条给出本周可取证据、 kill 标准与最便宜测试。

**评审中已独立核实的事实**（用于校准，不盲信 proposal 自述）：
- metric-factory HEAD 确为 `169faa8d…`、Node v24.21.0、依赖含 `@modelcontextprotocol/sdk ^1.30.1`、tsup/vitest/zod/commander 技术栈与 proposal §「已核对的事实输入」一致 ✅
- JuanerAI 插件合同四份文档存在于 `2c5c` 工作树（standard / acceptance-checklist / reference-adapter / README）✅
- 目标目录确为空目录 + `.flow/`，state.json 显示预算 60 turns / 12h、GRILL 2 轮 × 9 问、auto 模式 ✅

## Top Kill-Assumptions（按 影响 × 概率 × 测试便宜度 排序）

### K1 · 范围 vs 预算：7 页 + 双协议接缝 + 四分权 + 快照 + 10 失败路径，能在一个 60-turn/12h flow 内实现、测试并出浏览器证据

- **Claim**：方案.md 已把语义设计全部做完（对象、状态分层、失败语义均为「约束，非开放问题」），demo.html 证明了 UI 流程，所以本期工作「只是」把原型移植为真实本地服务 + 持久化 + 测试。
- **Steelman**：设计搅动的确被前置消灭了；metric-factory 提供了同作者、同技术栈的可运行参照（node:http + 静态资源 + 无数据库）；无外部依赖、无网络不确定性。
- **Attack**：指令 7 条每条都是一个子系统。仅 §08 状态分层就是 5 层 × N 态，失败路径 10 条各有独立状态机边；A01–A16 有 16 条分级验收。上一轮仅验证一个**静态 HTML** 的 46 项行为就花了一整个 session。metric-factory 是 CLI 优先的**设计态**工具（YAML 进、导出出），而 data-mcps 是**运行态**产品（长驻服务、取消传播、分页、原子多文件提交、按请求解析凭据）——参照物覆盖了外壳，不覆盖引擎。若 turn 预算在实现中途耗尽，交付物是「半个接线产品」，比一个收窄但完整的闭环更差。
- **Fails if**：完整表面（7 页面 + REST 适配器 + MCP 接缝 + 授权中间件 + 快照存储 + 10 失败路径 + 浏览器证据）无法在预算内全部达到「测试通过 + 证据留档」。
- **本周可取证据**：先做一个垂直切片——仅天气合成夹具的「集市 → 连接 → 查询 → 预览 → 保存 → 读回」+ **一条**失败路径（429），并记录消耗的 turn/时间。
- **Kill criterion**：切片消耗 >30% 预算（约 18 turns 或 3.5h）→ 立即砍范围（MCP 接缝降级为 feature-flag 桩、画像样板降为静态演示页、失败路径保留 429/取消/保存失败三条主路径），而不是继续全量铺开。
- **Cheapest test**：上述切片本身就是测试；零额外成本，且无论结果如何都是必须做的工件。

### K2 · 失败路径的深度：10 条路径各有真实行为，而非 10 条 toast 文案

- **Claim**：§08 表已给出每条失败的用户可见语义与允许的下一步（本地阻断请求数 0、费用未知 ≠ 0、未知不盲重试、迟到结果隔离），合成夹具可在适配器接缝确定性注入 401/403/429/超时/部分结果，行为可测。
- **Steelman**：这是本产品的差异化所在，且设计已完成；「可替换的测试接缝」正是为此而设；A02/A06/A07/A11 给出明确通过条件。
- **Attack**：风险不在设计在深度。「取消」要求 AbortController 穿透适配器、停分页、迟到结果不自动保存；「结果未知」必须是与「失败」不同的状态——多数实现会塌缩二者。更隐蔽的是：夹具若同步 resolve，取消永远不会真正竞态，测试会通过但行为是假的——「针对夹具验证的取消语义」可能不证明任何真实取消能力。在时间压力下，10 条路径最容易被做成 10 种提示文案。
- **Fails if**：取消/超时/未知仅在文案上可区分，行为上不可区分（例如「已取消」的运行实际已写入分页结果，或「未知」被 UI 当作「失败且免费」处理）。
- **本周可取证据**：夹具适配器支持「挂起响应」（held promise）后，跑一个测试：查询中取消 → 状态机走「取消处理中」→ 迟到 resolve 被隔离不入快照。
- **Kill criterion**：上述测试无法在不重写执行层的情况下通过（即执行层没有贯穿的 abort/identity 设计）→ 砍失败路径数量到 3 条主路径并明确降级声明，不留「假取消」。
- **Cheapest test**：一个测试文件 + 一个可挂起的夹具；约 1–2 turns。

### K3 · 存储决策的时机与原子性证据：「自行决定」不能变成「最后决定」

- **Claim**：snapshot 不可变 + 原子提交 + 独立读回，用 metric-factory 已验证的「版本化文件、无数据库」路线即可达成（写临时 → 校验 → 原子提交 → 读回；§07/§13）。
- **Steelman**：macOS/APFS 同目录 rename 原子性可靠；内容寻址 + SHA-256 在 demo 中已做过；方案 §13 明确要求「先验证原子保存、损坏恢复再选型」。
- **Attack**：proposal 把存储形态列为开放问题——合理，但「同一运行重试保存不重复扣费查询」「派生快照保留父链」「不可原地覆盖」要求 run id / snapshot id / 幂等键的身份设计**先于**保存路径存在。若查询/预览代码先按某个假定的存储形态写好再回填存储，返工成本落在预算最紧张的尾部。且 A11 grading 的是「坏 hash/缺文件读回拒绝、不回退伪成功」——没有损坏演练的原子性只是宣称。
- **Fails if**：存储选型晚于查询/保存路径编写；或原子性无 kill-9/字节翻转证据。
- **本周可取证据**：第 1 天内落一份 ≤1 页的存储决策记录（文件 vs SQLite + 身份/幂等键设计），并做损坏演练：写完快照翻转一字节 → 读回拒绝；提交中途杀进程 → 登记要么完整要么不存在。
- **Kill criterion**：决策记录在第 1 天结束时仍不存在，或损坏演练暴露需要引入数据库迁移/复杂恢复 → 立即选最简方案（版本化目录 + 同目录 rename + manifest SHA），禁止再议。
- **Cheapest test**：决策记录 + 一个 corruption 测试脚本；<1 turn。

### K4 · MCP 接缝的投入产出：为一个无近期触发场景支付多少保费

- **Claim**：指令 #3 要求保留 MCP 接入能力；@modelcontextprotocol/sdk 1.30.1 已在参照栈中验证；合成 Server（in-process）是标准模式，白名单 + 指纹比对只是逻辑。
- **Steelman**：合成 Server 测试接缝是公认做法；本期不安装任何第三方 MCP，安全边界干净；方案 §14 明确「它不证明外部 MCP 连通」，无过度宣称。
- **Attack**：真正的风险不是合成 Server 测不出真东西（proposal 自己承认了），而是：(a) 接缝由客户端同一作者设计，会共享作者的盲区——真实 Server（如 Alpha Vantage 官方 MCP）带来的是远程 OAuth、streamable HTTP、session 管理、协议版本skew，合成 Server 一条都测不到；(b) 天气主线是 REST，方案 §13 明确「REST 无需包成 MCP」，MCP 接缝本期没有任何已授权的真实 Server 可对验；(c) 它消耗的每一 turn 都从 K1/K2 的验收项里抽血。若 MCP 接缝成本 >15–20% 预算，就是为无触发场景付超额保费。
- **Fails if**：接缝抽象（传输假设、鉴权模型、能力模型）撑不过第一个真实 Server；或为建它挤占 A01–A16 实际 grading 的失败路径/质量工作。
- **本周可取证据**：编码前把适配器接口对着**两份书面规范**做纸面设计（SDK 类型 + Alpha Vantage README 工具清单）；若纸面阶段就发现需要的不止「1 个接缝文件 + 1 个合成 Server + 白名单测试」，降级。
- **Kill criterion**：纸面设计显示接缝需要 >3 个工件或引入 OAuth/远程传输任何一项 → 砍为 feature-flag 桩（接口定义 + 合成 Server 冒烟，不进 UI 主流程），把预算还给 K1/K2。
- **Cheapest test**：纸面设计评审，30 分钟，零代码。

### K5 · R1 退出条件的静默修订：「合成即交付」与方案 §14 的 R1 退出条件不一致，需显式记录并与用户确认

- **Claim**：proposal 交付「可运行的独立产品」，本期 A16 保持「未执行」，外部数据边界全为合成夹具。
- **Steelman**：这是**用户自己的指令 #2** 明确规定的（「外部数据边界使用明确标注的合成夹具」「真实供应商请求需另行明确授权」）——所以「用户可能期待真实调用」这一攻击基本被用户原话自我驳倒。
- **Attack**（残余部分，非全文）：方案 §14 的 R1 退出条件原文含「获准的小样真实读取与快照独立读回」。proposal 实际把 R1 重新定义为「合成全绿 + 接缝存在 + A16 未执行」。这是一个**静默的 spec 修订**：若 PRD/GRILL 继承此定义而不标注，未来任何对照方案 §14 的审计都会判 R1 未达退出条件。修订本身合理（授权约束），但必须显式化。
- **Fails if**：重新定界未记录、未确认，交付时按方案 §14 原退出条件被判定「R1 未完成」。
- **本周可取证据**：GRILL 第 1 轮向用户确认一句：「本期 R1 退出条件修订为：合成正负例全绿 + 适配器接缝 + 浏览器证据；真实小样读取移至授权后。是否接受？」并在 PRD 中写明修订。
- **Kill criterion**：用户回答「不接受，本期必须含至少一次真实小样读取」→ 暂停实现，先走授权对话（Open-Meteo 免 key 非商业小样的授权成本极低，是可行退路），再重排计划。
- **Cheapest test**：GRILL 2×9 中的一个问题；成本为零，且 state.json 显示 GRILL 本来就要跑。

## What's Well-Reasoned（不制造怀疑，以下断言经得起攻击）

- **对象边界与状态分层作为「约束，非开放问题」前置锁定**（§03/§08）：消灭了实现期设计搅动，这是本 proposal 最强的结构性优势。攻击面只剩执行深度，不在方向。
- **权限四分 + 默认模型外发关闭**：单用户本地范围使「企业 IAM 过度设计」的攻击不成立；A04/A05/A15 给出精确通过条件，且可用合成敏感标记测试，无需真实凭据。**唯一软点**：服务端强制不能退化为「只禁按钮」（§09 已明文要求，但需在测试里用 4 条无授权 HTTP 请求各打一次——成本极低，建议并入 K2 的测试文件）；Keychain 不可用时「仅会话内存并明确提示」的回退必须真的可见，不能静默永远走内存。
- **技术栈与仓风延续 metric-factory**：我独立核实了 HEAD、Node 版本与依赖树，与 proposal 声称一致；同栈复用缩短启动。注意边界已在上文标注：外壳可移植，运行态模式（取消/分页/幂等）在参照物中无先例——这是事实陈述，不是否决。
- **证据纪律**：验证记录.md 诚实限定 46/46 只证明原型行为；proposal 复述了该限定；A16 主动留「未执行」而非伪造。全文未发现把合成当真实、把文档核对当账户连通的越界宣称。
- **「不做」清单**（Agent Runtime / 分析核心 / 通用插件市场 / 企业权限）与指令 #7 一致，范围蠕变的主要入口（宿主接线）被明文关闭。

## What I Couldn't Assess（plan 未给出足够判断材料）

- **本 dev-flow 实现的实际 turn 燃烧率**：仓内无历史数据，K1 的 30% 阈值是估计值，需切片实测校准。
- **auto 模式下实质问题能否真正阻塞**：state.json `mode: "auto"`；proposal 说实质问题「集中提出、继续不受影响的工作」——K5 的问题属于 definition-of-done 级别，它是否能在 auto 流中等到回答，机制上未验证。
- **demo.html 的 46/46 未在本次评审中重跑**（只读上下文，未执行浏览器）；依赖验证记录.md 的自述，但该记录的失败留痕（attempt01）增加了可信度。
- **存储形态**：proposal 刻意留白，无法攻击一个尚未做出的决定——只能攻击其时机（见 K3）。

---

**最终结论**：五条 kill-assumption 的 kill criterion 当前**均未触发**——K1–K4 的测试尚未执行（应在 flow 首日内执行，顺序即排名顺序），K5 的问题尚未提问（GRILL 第 1 轮零成本确认，且有用户指令 #2 原文作为强先验支持「接受」）。本 proposal 的证据纪律与前置设计质量高于平均水平，不存在「已在 kill 标准上失败」的承重假设。

**verdict: go**
